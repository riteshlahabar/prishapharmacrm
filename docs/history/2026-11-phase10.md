# 2026-11-22 — Phase 10: the telecaller Flutter app

Repo: `prishapharmatellecallerapp`, branch `claude/happy-ramanujan-zthjt1`.

- **The scaffold was dead and would not install.** It targeted `/user`,
  `/customers`, `/call-schedules`, `/dashboard`, `/reports` — none of which
  exist — and pinned `flutter_riverpod: ^2.61.0`, never published, a typo
  for 2.6.1, so `pub get` failed. Rebuilt on the Phase 6 contract.
- **Five surfaces:** login, queue, log-a-call, call-backs, sent messages.
- **The queue is one request.** `/persons` is region-scoped server-side and
  each row carries `last_call`, shaped by the Calls module's own resource —
  so a row shows its outcome and whether a call-back is due without asking
  again. Tapping dials (`url_launcher`).
- **One rule mirrored, not duplicated.** The API requires `follow_up_at` on
  `callback` and refuses it elsewhere, so `CallStatus.needsFollowUp` decides
  whether the field shows *and* whether it is sent. Repository tests assert
  the body: the date goes as plain `Y-m-d H:i:s`, a non-callback never
  carries one even with a stale value on the form, and neither
  `telecaller_id` nor `called_at` is sent.
- **Writes refresh together.** Logging a call closes any open call-back on
  that person server-side, so one action invalidates queue, call-backs and
  history together.
- **Package ids are real now:** `com.prishapharma.telecaller` and
  `com.prishapharma.mr` — namespace, applicationId, the MainActivity package
  and directory, and the iOS bundle id — closing the `com.example` blocker.
  Also declared INTERNET outside the debug manifest and the `tel:` intent
  under `<queries>`: without it Android 11+ resolves the dialler to nothing.
- Verified by a clean `flutter analyze` and 34 tests, on fixtures captured
  live including the API's three `follow_up_at` rejections. MR app
  re-checked after its rename: clean, 40 tests.
- **Not done:** no device here, so neither app has run on real hardware, and
  both keep the token in `SharedPreferences`.
