# 2026-11-21/22 — Phase 3: MR backend (attendance, visits)

- `attendances`: one row per MR per day, unique `(mr_id, date)`. The service
  checks the day's state first and returns a clean 409; the unique index is
  the real guard, for two requests racing from a flaky mobile connection.
  The loser re-reads after the insert so it cannot overwrite the winner.
- Every timestamp is server-set. The device posts coordinates only, so a phone
  with a wound-back clock cannot forge a shift. `GET /attendance/today`
  answers even on a day with no row, so the app's two buttons never guess.
- Conflicts are **409 with `errors.reason`**, not 422: the payload was fine,
  the day's state forbade the call. `already_checked_in`, `not_checked_in`,
  `already_checked_out`.
- `visits` keeps three clocks on purpose — the times the MR states, when the
  device read the GPS (`location_fetched_at`), and when the server received it
  (`created_at`) — so a visit filed hours late is visible as one. `person_id`
  is `restrictOnDelete`: losing a person must not erase the call history.
- `mr_id` comes from the token in both modules; `StoreVisitRequest` does not
  accept it. Validation: `out_time ≥ in_time`, no future `visit_date`, lat and
  lng together or neither, person must be active.
- Scoping went in the service, not the controller. `paginateForUser` was there
  already, but `summary()` and `show`/`destroy` were not scoped — a telecaller
  with `visits.view` saw system-wide counters and could open any visit by id.
  Added `summaryForUser` and `findForUser`; out of territory reads as 404, not
  403, since 403 confirms the row exists.
- Attendance stays MR-wide on purpose: presence is not a territory question.
- Fixed three pre-existing Cuba JS bugs found while checking the new pages —
  every detail page threw on load. See `docs/ui-theme-patches.md`.
- Smoke suite for the phase: 62 checks green, plus a 22-route authenticated
  sweep of the panel.
